# 2026-08-20 — Sync v1: specification

**Status:** **RATIFIED by the owner 2026-08-21**, after one adversarial review round
(§11) and `CKSyncEngine` verification against live Apple documentation (§4.1.1). All
three gates in §10 are closed. The owner ratified after a full plain-English walkthrough
of §1–§9, including the two deliberately-accepted lossy cases (§3.5) and the five shipped
defects (§5).

**Authority:** owner decision **D16** (sync v1 is Apple devices via iCloud, with no
app-level login; v2 adds web through a pairing code) and **D15** (sync is a Pro feature),
recorded in
[`../../reviews/2026-08-20-gear-model-owner-decisions.md`](../../reviews/2026-08-20-gear-model-owner-decisions.md).

**Why this exists before web ships.** The [gear spec](2026-08-20-gear-model-v2-spec.md)
§4 designed the gear envelope *for* sync, but that was analysis inside a schema document,
not a reviewed specification. Web is the first surface to write the gear format and
therefore freezes it (D14). If sync later needs a different record model, the format is
already in real users' browsers. This spec closes that gap — and it found **five** defects in a
**shipped** store that sync would have turned into data loss (§5).

**Scope.** What syncs, how records merge, and what the transport must guarantee. It does
**not** specify UI, the Pro purchase flow, or the v2 pairing code beyond its constraints.

## 1. What syncs, and what deliberately does not

| Store | Syncs | Reason |
|---|---|---|
| `3dpa_gear_v1` / `gear.json` | **yes** | the feature's whole purpose |
| `3dpa_workshop_v1` / `workshop.json` | **yes** | "Workshop, gears and inventory follow you across devices" |
| Inventory (Train 2) | **not committed** | Inventory ships after 2.0 (D18), and **D18b leaves local-first vs. server-backed unresolved**. A server-backed inventory would not sync through this mechanism at all. This spec covers it *if and when* it becomes a local store; it cannot promise it now. |
| `3dpa_state_v1` / `app-state.json` | **no** | the last configurator session. Syncing it would make the phone jump to whatever the iPad was doing mid-configuration — a live cursor, not a document. |
| `3dpa_theme` / Appearance | **no** | legitimately per-device: a Mac in daylight and a phone at night are different situations. |
| `3dpa_lang` | **no** | an **explicit user toggle** (`engine.js:27`), not a mirror of the device language — but still a per-device choice, and a Danish phone alongside an English work Mac is a normal arrangement. |
| `3dpa_notrack` | **no** | a privacy choice about *this device*. Copying it across devices overrides a decision the user made in one place only. |
| `notification-state.json` | **no** | holds a device push token; meaningless anywhere else. |

The distinction is **documents vs. session**. A gear and a saved profile are documents the
user owns and expects to find everywhere. The current configurator state, the theme and
the language are properties of *this device right now*. Syncing session state is the
classic way to make sync feel haunted.

### 1.1 The gear `settings` record, field by field

The ratified gear envelope carries a `settings` object (gear spec §2.2) whose three fields
are not all the same kind of thing, and lumping them together would get at least one
wrong. Each takes its own rule, and each rule is conflict-free:

| Field | Syncs | Merge |
|---|---|---|
| `active_gear` | **yes** | LWW on `settings.updated_at`. Which gear you are working with is a document-level choice, and a dangling pointer already has a defined fallback (gear spec §4.3), so a stale value is harmless. |
| `catalog_seen` | **yes** | **max wins** per counter. "I have seen up to N printers" only ever grows; taking the higher value means the news line does not reappear on a second device for something already read. |
| `save_prompt_dismissed` | **yes** | **OR** — dismissed on any device is dismissed everywhere. The user said "stop offering this," not "stop offering this here." |

None of the three can conflict destructively, which is why `settings` being one record is
safe despite holding three unrelated things.

## 2. Record model

**Sync is per record, never per file.** Each gear is a record; each Workshop profile is a
record; settings is one record per store. The local envelope is a materialized view the
app reads from — never the unit of synchronization.

Two independent reasons, both decisive:

1. **Correctness.** One file synced as one file is last-write-wins over the entire
   collection, so the slower device's new gear silently disappears.
2. **A hard platform limit.** A CloudKit record is capped at **1 MB** — verified 2026-08-21 against Apple's CloudKit data-size limits table (*"Maximum record size (not including Asset fields): 1 MB"*; assets are separate at 50 MB). A Workshop profile
   carries a full configurator state plus its print journal; a user with a large shelf
   would eventually exceed that as a single blob. Per record, the ceiling is never
   approached.

Record identity is the entity's own id — the map key for gears (gear spec §2.3), the
`id` field for Workshop profiles.

## 3. Merge rules

There are three shapes of data here, and they need three different rules. Applying
last-write-wins to all of them loses data in two of the three cases.

### 3.1 Value fields — last-write-wins

Fields that hold *a choice*: a gear's `name` and `fields`, a profile's `name`, `notes`
and `state`.

- later value-timestamp wins, compared per record
- **an array of pinned values is still a value.** A gear's `fields.useCase` is one choice
  expressed as a set, not an accumulating log, so it takes LWW like any other field.

**A value timestamp must move only on a value edit.** This rule has now been violated
twice in this codebase in the same way, which is why it is stated as a rule rather than as
a fix:

| Where | What bumps the value timestamp when it should not |
|---|---|
| Gears (designed, not yet built) | *using* a gear — closed by splitting `last_used_at` from `updated_at` |
| Workshop (**shipped**) | *logging a print outcome* — `addOutcome` sets `p.updated = _now()` (`workshop-store.js:201`), and `removeOutcome` does the same (`:213`) |

The Workshop case is a live defect and it loses real edits. Concretely: device A renames a
profile at t1; device B, still holding the old name, logs a print outcome at t2. B's write
bumps `updated`, so **B's stale name, notes and state beat A's rename** — while the
journal entry that actually changed merges fine. The user loses the edit they made
deliberately and keeps the one they made incidentally.

Filed as **D-3** (§5). The fix is that journal writes touch a journal timestamp, never the
value timestamp.

### 3.2 Collection fields — union by id, with tombstones

Fields that *accumulate*: the Workshop print journal (`profile.journal`).

Union by entry id, never LWW. Two devices recording different print outcomes for the same
profile must both survive — an outcome is a historical fact, and discarding one discards
something that actually happened.

**Union alone is not enough, because outcomes can be deleted.** `removeOutcome`
(`workshop-store.js:206-215`) hard-deletes an entry, and the UI exposes it as a button
(`app.js:1089`). Under plain union-by-id a deleted outcome is resurrected by any device
still holding a copy. Journal entries therefore need **per-entry tombstones** exactly as
records do. Filed as **D-4** (§5).

Declaring outcome deletion "local only" was considered and rejected: the button exists and
users press it, so the deletion has to travel.

**LWW is applied per field-group, not to the whole record.** A profile whose `name` came
from device A and whose journal holds entries from both A and B is the correct result, not
a compromise.

### 3.3 Operation logs — op-union

Workshop personal tuning already works this way, deliberately: `workshop-store.js` merges
tuning *"by op-union (fork-lossless, idempotent)"* (`:224-225`). It is already
conflict-free and is the precedent the other two rules were measured against — the only
part of the existing code designed for forking.

**Record model.** Tuning is not a profile and needs its own answer. `tuning.accepted` and
`tuning.dismissed` live at the envelope level (`workshop-store.js:72`), not inside any
profile. Tuning syncs as **one record per `pairKey` + `offsetKey` entry**, each carrying
its own `ops` array merged by op-union. Not one ledger record (which would reintroduce
whole-collection LWW and the 1 MB ceiling) and not one record per op (which would multiply
record count for no benefit, since op-union already makes the entry conflict-free).

**`revertTuning` caveat, which must be stated because it is surprising.** Revert appends a
negating op for the ops it can currently see (`workshop-store.js:122`). Under sync, an
accept that arrives from another device *after* a revert survives it — the revert negated
what it knew about, not what the other device was doing. This may well be the behaviour
the user wants (their newer accept stands), but it is emergent rather than designed, and
the plan must decide whether to keep it or make revert a tombstone over the entry.

### 3.4 Deletion

**A tombstone wins over a concurrent edit, regardless of timestamps.** With plain LWW a
device that had the item open could resurrect something the user deliberately deleted, and
a returning deletion alarms a user far more than a lost edit does.

Tombstones sync. A delete that does not travel is a delete that undoes itself.

### 3.5 What is still lossy, stated plainly

Two cases, and the first is broader than an earlier draft admitted:

1. **A gear is whole-record LWW** (gear spec §4.2), so concurrent edits to *different*
   fields of the same gear still lose one: A renames the gear while B pins `useCase`, and
   the later write takes the whole record. Making this lossless needs per-field
   timestamps, which is a real cost for a single-user app where two devices rarely edit
   one gear at the same second. **Accepted deliberately, not overlooked** — an earlier
   draft described the loss as "same value field," which understated it.
2. **A Workshop profile's value fields** lose the same way among themselves, though its
   journal does not (§3.2).

What is **not** accepted, and is closed above: losing a whole record, resurrecting a
deletion, a read outranking a write, or losing an appended journal entry.

## 4. Transport

### 4.1 v1 — CloudKit private database

The device's existing iCloud account is the identity. No app-level account, no password,
no sign-in screen, no server to run, and no per-user cost (D16).

The app's deployment target is already **iOS 17.0**
(`project.pbxproj:774`), so Apple's newer sync API (`CKSyncEngine`, iOS 17+) is available
**without raising the floor**. It is the expected implementation path, since it handles
change tracking, retry and scheduling, leaving this spec's merge rules as the part that
must be written by hand.

> **Verification gap — CLOSED 2026-08-21.** The documentation was retrieved on the second
> attempt. The page is a JavaScript shell; its content lives at the DocC data endpoint
> (`developer.apple.com/tutorials/data/documentation/cloudkit/cksyncengine-5sie5.json`),
> reachable via the framework index at `/tutorials/data/index/cloudkit`. The earlier
> research failed on the HTML URL, not on the documentation being absent. Findings in
> §4.1.1; nothing below rested on a wrong premise.

#### 4.1.1 What the live documentation confirms (fetched 2026-08-21)

**Availability.** `final class CKSyncEngine` — iOS 17.0, iPadOS 17.0, Mac Catalyst 17.0,
macOS 14.0, tvOS 17.0, watchOS 10.0. The app's target is `IPHONEOS_DEPLOYMENT_TARGET =
17.0` (verified in `project.pbxproj` this session), so the floor claim holds: **available
without raising it.**

**It does not merge, and that is the answer to §9.1.** Apple states plainly: *"CKSyncEngine
does not handle errors that require application-specific logic. For example, if you try to
save a record and get a `serverRecordChanged`, you need to handle that error yourself."*
There is therefore **no built-in last-write-wins to fight** — the engine is change
tracking, batching, scheduling and retry, and every merge decision is the app's. §3 is
fully expressible as written, and the feared fallback ("the merge moves into the adapter
and the engine carries opaque payloads") is not needed, because that is already the
design.

Better than §3 requires: a `serverRecordChanged` `CKError` exposes **`clientRecord`,
`serverRecord` and `ancestorRecord`** — *"the original version of the record"* — so
three-way merge material is available. §3.2's per-field-group merge and §3.4's tombstone
precedence are both implementable directly.

**State serialization is opaque and the app owns it.** *"The sync engine uses an opaque
type to track its internal state, and it's your responsibility to persist that state to
disk and make it available across app launches."* State arrives as a `stateUpdate` event
that the delegate must persist alongside app data. This confirms §6's device-backup row
rather than merely assuming it: a restored device can discard its serialized state and
re-sync.

**Automatic retry covers less than the transient set implies.** The engine self-handles
`notAuthenticated`, `accountTemporarilyUnavailable`, `networkFailure`, `networkUnavailable`,
`requestRateLimited`, `serviceUnavailable` and `zoneBusy`, honouring retry-after. Every
other error — including all of §6's — is ours.

**Account changes are a first-class event.** `accountChange` carries
`signIn(currentUser:)`, `signOut(previousUser:)` and `switchAccounts(previousUser:currentUser:)`,
which is exactly the hook §6's "account switched or signed out" row needs to keep local
data out of a stranger's iCloud. Apple: *"It's your responsibility to react appropriately
to this change and update your local persistence."*

**Two new constraints this spec did not carry.** Both are planning inputs, not blockers:

1. **Entitlements.** `CKSyncEngine` *"requires the CloudKit and Remote notifications
   entitlements"* plus background execution modes. That is a capability + provisioning
   change on the iOS target, not just code. The app already ships push (1.1.0
   notifications), so the ground is not new, but the plan must name it as a task.
2. **Private database only.** *"Don't use `CKSyncEngine` to sync your app's public
   database."* This spec uses the private database (§4.1), so it is a constraint we
   already satisfy — recorded so no later feature reaches for the public one.

**Subscriptions are automatic.** The engine discovers an existing `CKDatabaseSubscription`
or creates one. No manual subscription plumbing in the plan.

**Sync timing (§9.3) is partly answered.** Scheduling is deliberately indeterminate —
*"depending on good system conditions"* — with `fetchChanges(_:)` and `sendChanges(_:)` for
the cases that must not wait. So the plan chooses only the *manual* trigger points; the
routine cadence is not ours to set.

### 4.2 v2 — web via a pairing code

Later (D16). One constraint belongs on the record now: **a pairing code needs a server.**
The device shows a code, web enters it, and something in the middle has to hold the data
and match the two. That reintroduces exactly the running cost and operational burden that
choosing iCloud removed. It is a real decision when it arrives, not a free extension.

The same problem governs **Pro entitlement on web**: a purchase made in the App Store is
proved by the device's App Store account, and a browser has no access to it. Web Pro needs
either its own purchase path or the pairing link. Recorded because the owner has already
asked for web Inventory access to Pro buyers.

## 5. Defects sync exposes in shipped code

All in `workshop-store.js`, which is **live and has users**. Every one would become data
loss the day sync is switched on. None is a sync bug — sync is what makes them visible.
Each was verified in the code, not inferred.

### D-1 · Workshop deletes have no tombstone

`remove(id)` filters the row out of the array (`workshop-store.js:176-180`). The record is
simply gone. Under sync, a device that still holds the profile re-uploads it and the
deletion undoes itself.

**Fix:** an `archived_at` field on the profile record, exactly as gears use. **Additive
and backward-safe** — existing envelopes and existing user backup files lack the field,
and absent correctly reads as "not deleted," so old backups keep importing. The Workshop
list's behaviour does not change; only the storage does.

### D-2 · `importJSON`'s merge is direction-dependent

The current merge keeps existing profiles and lets *"imported entries win on id
collision"* (`workshop-store.js:224`, merge at `:228`). For a user-initiated backup
restore that is right — the user chose to import. **For sync it is wrong**, because
"incoming" means nothing between peers.

**Fix:** sync does not reuse `importJSON`. It needs a timestamp-aware merge implementing
§3. The tuning op-union half *is* reusable and should be reused rather than rewritten.

### D-3 · Journal writes bump the value timestamp

`addOutcome` sets `p.updated = _now()` (`workshop-store.js:201`); `removeOutcome` does the
same (`:213`). Logging a print outcome therefore makes that device's *stale* name, notes
and state win the next value conflict (§3.1).

**Fix:** a separate journal timestamp. Journal writes must not touch the value timestamp.
Additive; old records without it default to the existing `updated`.

### D-4 · Journal entries can be deleted with no tombstone

`removeOutcome` (`workshop-store.js:206-215`) hard-deletes, and `app.js:1089` wires it to a
visible button. Under union-by-id the entry is resurrected by any device still holding it.

**Fix:** per-entry tombstones on journal records (§3.2).

### D-5 · A version-mismatched read is destructive

`_read()` returns `[]` when `env.v !== VERSION` (`workshop-store.js:35`), and any
subsequent `_write` persists that empty result over the original data. Locally this has
never mattered — there has only ever been one version. **Under sync and cross-platform
version skew it is a data-loss bug:** an older client that meets a newer envelope reads it
as empty and can then overwrite it.

**Fix:** the hostile-envelope posture the gear spec already specifies (gear spec §2.5) —
preserve what cannot be understood, never overwrite it, and surface the skew. This is the
one fix here that is not purely additive, and it should land early for that reason.

## 6. Failure and edge cases

These are the cases that decide whether sync feels trustworthy, and they are cheap to get
wrong.

| Case | Required behaviour |
|---|---|
| **iCloud disabled or unavailable** | The app works fully. Sync is an enhancement, never a gate. A user who never turns it on loses nothing and sees no degraded state. |
| **Offline** | All writes are local and complete. They upload when connectivity returns. Nothing waits on the network. |
| **iCloud account switched or signed out** | Local data **stays local and is not uploaded into the new account.** The app treats it as a fresh sync context. Leaking one person's gears into another's iCloud is the worst outcome available here. |
| **Device offline for a long time** | It returns with old timestamps and correctly loses value conflicts, while its unique records and journal entries survive by §3.1–3.3. |
| **First sync, local data + empty cloud** | Upload. |
| **First sync, empty local + cloud data** | Download. |
| **First sync, both populated** | Union by id, LWW on collision. **No "which one do you want to keep" dialog** — the merge rules exist precisely so the user is never asked to adjudicate their own data. |
| **Pro lapses** | Sync stops. **Nothing is deleted, locally or in iCloud.** Re-subscribing resumes where it left off. Data is the user's; access to the syncing of it is what was bought. |
| **Two devices first-syncing simultaneously** | Both may try to create the zone. Creation must be idempotent — "already exists" is success, not an error. |
| **User deletes the app on one device** | Not a delete. Cloud data survives; reinstalling downloads it. Only an explicit in-app "delete my synced data" removes anything. |
| **Restore from a device backup** | The restored device may hold stale sync metadata describing a state the server has moved past. It must be able to discard its local sync state and re-sync from scratch without losing local-only records. |
| **The user deletes the iCloud zone** (from Settings) | `userDeletedZone` is an explicit instruction, not an error. Stop syncing, keep local data, do not silently recreate and re-upload. |
| **Change token expired** | The server can invalidate an incremental cursor. Fall back to a full fetch; never treat it as "no changes." |
| **`serverRecordChanged`** | The normal conflict path, not a failure: re-apply §3's merge to the server record and retry. |
| **Record not found on fetch** | It was deleted elsewhere. Treat as a tombstone, not as an error to retry. |

**Four different failures share the word "quota"** and they have different recoveries, so
the implementation must not collapse them:

| | Meaning | Recovery |
|---|---|---|
| `localStorage` quota | the browser's per-origin cap | the existing `{ok, error: 'quota'}` path; the write did not happen |
| CloudKit `quotaExceeded` | the user's **iCloud storage** is full | the user must free space; retrying is pointless. Say which one it is. |
| request `limitExceeded` | the batch exceeded the server's **250 records per request** (saves plus deletes combined, per the `CKSyncEngine` documentation, fetched 2026-08-21) | split the batch and retry — recoverable without the user. Building batches with `init(pendingChanges:recordProvider:)` bounds them automatically and leaves the overflow in `pendingRecordZoneChanges` for the next call, so this should never be reached. |
| record over **1 MB** | one record is too big | a design error, not a runtime condition. §2's per-record model exists so it cannot happen. |

**Clock skew.** `updated_at` is device time; a badly wrong clock wins conflicts it should
lose. Accepted, and **not** presented as a guarantee. If it ever must be one, the fix is a
per-record counter incremented on write, compared ahead of the timestamp — an additive
field needing no migration, which is why deferring is safe.

## 7. Privacy

- Sync is **opt-in**. The app is fully functional with it off.
- Data lives in the user's **own** iCloud private database, not on any server operated by
  this project. There is no account to breach because there is no account.
- The engine stays on-device. Sync moves the user's documents; it does not move
  computation.
- Nothing about `3dpa_notrack` changes: it is a per-device choice and §1 keeps it local.

The design's Settings artboard promises *"End-to-end encrypted."* CloudKit's private
database is encrypted in transit and at rest, and Advanced Data Protection makes it
end-to-end for users who enable it — **but that is the user's account setting, not
something this app can assert on their behalf.** The wording in the shipped UI must be
accurate about which of the two it means; claiming E2E unconditionally would be false for
most users.

## 8. What this does not solve

- Real-time or collaborative editing. Sync here is eventual and single-user.
- Web in v1 (D16), and therefore web Pro entitlement (§4.2).
- Merging concurrent edits *within* a text field. Notes take LWW like any other value.

## 9. Open questions

1. ~~**Does `CKSyncEngine` express §3?**~~ **ANSWERED 2026-08-21 (§4.1.1): yes, fully.**
   The engine performs no merging at all and hands `serverRecordChanged` back to the app
   with `clientRecord`, `serverRecord` and `ancestorRecord`. There is no whole-record LWW
   to work around, so §3.2's per-field-group merge and §3.4's tombstone precedence are
   implementable directly rather than through an opaque-payload adapter.
2. **Does the Workshop backup file gain `archived_at` in exports?** Adding it is
   consistent; a user importing an old backup then sees archived rows return, which is
   arguably correct for a restore and arguably surprising.
3. **When does sync first run** — at launch, on change, or on foreground? **Narrowed
   2026-08-21:** the engine schedules automatically on an indeterminate cadence, so the
   plan chooses only the *manual* `fetchChanges`/`sendChanges` trigger points (§4.1.1).
   Still a plan-time question, but a smaller one.
