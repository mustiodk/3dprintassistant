# iOS 1.1.4 release design

**Status:** DRAFT — owner-approved scope; written spec awaiting owner review.

**Date:** 2026-08-13.

**Release train:** iOS 1.1.4.

**Related issues:** [#12](https://github.com/mustiodk/3dprintassistant/issues/12), [#31](https://github.com/mustiodk/3dprintassistant/issues/31), [#35](https://github.com/mustiodk/3dprintassistant/issues/35).

**Detailed Elegoo decision:** [Elegoo in the primary brand row](2026-08-11-elegoo-primary-brand-design.md).

## 1. Decision and release intent

1.1.4 is a focused trust-and-parity release. It completes already-started accuracy
and catalog work, makes the top-level Output/export experience honestly bilingual,
and adds the one missing signal needed to evaluate the existing App Store review
prompt. It is not a general feature train and does not reopen parked intake work.

The release has two layers:

1. **Already landed in the current 1.1.4 branch:** acceleration safety clamp;
   bundled Ender-3 S1, FlashForge Adventurer 3 and Anycubic Kobra 2 Neo; full
   `epoxy_resin` support and persistence.
2. **Remaining before the train may ship:** Elegoo primary-brand parity; bounded
   EN/DA localization for Output-owned chrome; `review_prompt_requested`
   analytics across iOS, Worker, query and dashboard; durable App Store metadata;
   and final release verification.

The implementation plan must preserve that boundary. Already-landed work is
verified, not rewritten. Anything in §8 stays outside 1.1.4.

## 2. Product outcomes

The release is successful when:

- Elegoo appears in the iOS primary brand row, matching web, without narrowing
  remote-overlay compatibility for older app versions.
- A Danish device sees Danish top-level Output headings and export/error chrome;
  an English device sees English; unsupported locales safely fall back to English.
- The owner dashboard shows how many eligible review requests the app made for
  a selected platform/date range, including an explicit `0` rather than an
  absent or ambiguous row.
- App Store copy no longer contains brittle catalog counts and accurately
  describes export availability.
- The final iOS binary retains all already-landed 1.1.4 behavior, passes the
  complete release gates, and is not pushed or dispatched to TestFlight before
  the existing iOS push gate is satisfied.

## 3. Delivery surfaces

| Outcome | Source-of-truth surfaces | Delivery |
|---|---|---|
| Elegoo primary row | iOS bundled `data/printers.json` + XCTest | Next iOS binary only; no overlay mutation |
| Output EN/DA | `Strings.Output`, `en.lproj`, `da.lproj`, top-level `OutputView` chrome | Next iOS binary |
| Review-request count | iOS analytics sender, `/api/analytics`, analytics query, `/analytics` dashboard | Web analytics surfaces first; iOS event with binary |
| Store listing accuracy | Version description/release-note copy prepared in repo | Owner applies in App Store Connect |
| Release confidence | Web tests, iOS XCTest/UI tests/build, parity and metadata checks | Exact final HEAD only |

## 4. Detailed design

### 4.1 Elegoo bundled-catalog parity

Change only the iOS bundled `elegoo` brand row from `primary: false` to
`primary: true`. Do not change its `sort_order`, any printer row, the remote
overlay, or `min_app_version`.

The live contract becomes the ordered primary-brand IDs:

```text
bambu_lab, creality, prusa, anycubic, qidi, elegoo
```

Their sort orders must be the contiguous range `1...6`. An XCTest must load the
real bundled catalog and assert both the exact ordered set and contiguity. This
guards the user-visible curation decision rather than merely testing a fixture.

After the field flip, the recursively compared web/iOS `engine.js` + `data/`
trees are expected to be byte-identical. Any remaining difference is a stop
condition, not an accepted baseline.

This is deliberately a bundled change. The overlay route remains declined
because older pre-override builds can reject the complete overlay on a bundled-ID
collision. 1.1.4 must not trade printer delivery to older installs for a cosmetic
picker reorder.

### 4.2 Output-owned EN/DA localization

The scope is the complete public API of `Strings.Output` plus top-level
Output/export error chrome owned directly by `OutputView`. This includes section
headings, detail-level labels, back/export actions, export availability and
failure messages, invalid-state copy, the export-failure alert title, `OK`, and
`Report Issue`.

It does **not** mean every nested Output subcomponent is localized. Parameter
labels, slicer/product names, generated profile values, and strings owned by
`FilamentTab`, warning/detail components or other string namespaces remain
unchanged unless required to prevent a newly localized top-level state from
falling back to a hardcoded English label.

Implementation seam:

- add `Resources/en.lproj/Localizable.strings` and
  `Resources/da.lproj/Localizable.strings`;
- preserve the existing `Strings.Output` Swift API so call sites do not acquire
  locale branching;
- replace its literals with namespaced `NSLocalizedString` keys such as
  `output.export.unavailable`;
- use `%@` placeholders and locale-aware `String(format:locale:arguments:)` for
  formatted copy;
- wire the currently hardcoded Output alert title/buttons through the same
  namespace;
- keep English as the development-region fallback;
- add `Localizable.strings` inside the existing XcodeGen-managed `en.lproj` and
  `da.lproj` resource directories, then regenerate the project and verify that
  Xcode recognizes them as one localized resource/variant group. The directories
  and language regions already exist; their presence alone is not new evidence
  that string-table lookup is wired correctly.

Automated acceptance tests must load both language bundles directly and assert:

1. every declared `Strings.Output` key exists and is non-empty in both bundles;
2. the two bundles expose the same exact Output key set;
3. placeholder signatures match for formatted keys;
4. English fallback resolves safely for an unsupported locale.

A separate rendered Danish Output walkthrough must verify that top-level
export/error chrome has no truncation or mixed-language state at supported
device sizes.

This design intentionally avoids adding more `usesDanish` ternaries. Broader
language architecture and German are discovery work in #37; 1.1.4 creates a
clean resource-backed seam without pre-deciding that larger migration.

### 4.3 Review-prompt request analytics

The existing eligibility policy is unchanged: four distinct successful
profiles, three elapsed days, 30-day cooldown, 14-day feedback cooldown,
once per marketing version, and suppression on TestFlight/sandbox builds.
StoreKit provides no callback proving that the prompt was displayed, so the
event name and dashboard language must say **requested**, never **shown**.

Add the event:

```text
review_prompt_requested
```

The iOS payload contains only the existing common properties:

```text
platform, channel, appVersion, buildNumber, locale
```

It must not contain a profile, printer, user/session/device identifier, free
text, eligibility details or generated output. No Analytics Engine blob-schema
expansion is needed.

The ordered request path is:

1. call StoreKit `requestReview()`;
2. immediately persist `markReviewRequested()`;
3. send `review_prompt_requested` asynchronously as best-effort telemetry.

Persisting local state before awaiting the network preserves the user-facing
once-per-version contract even when analytics is unavailable. Analytics failure
must be silent and must never retry the StoreKit request. The existing
same-version gate prevents duplicate events when the app revisits the task.

The web contract adds the event to:

- the Worker's exact event/property allowlist;
- the `review_prompt_requested:ios` Analytics Engine index;
- the analytics query `features` result;
- the dashboard event label and feature breakdown;
- a dedicated `Review requests` KPI/quick fact that renders an explicit zero for
  the selected platform and date range.

The KPI is load-bearing. A chart that filters zero-count rows cannot distinguish
"instrumentation is working and no request occurred" from "the event was never
wired"—the precise uncertainty behind #12.

Tests must prove the exact iOS event name and common-only payload, Worker
acceptance and index writes, rejection of extra properties, query inclusion,
dashboard label/rendering, and explicit-zero behavior. Existing review-policy
tests remain authoritative for eligibility and once-per-version behavior.

TestFlight cannot demonstrate a real prompt because suppression there is
intentional. Do not add a production bypass or claim prompt-display evidence.

### 4.4 Durable App Store metadata

Prepare version metadata in the repository before App Store Connect entry. The
description must replace the stale exact catalog claim with durable wording:

- **80+ printers across 14 brands**;
- **19 filament profiles**;
- native profile export where the slicer publishes a matching machine preset,
  with a clear text fallback everywhere else.

Do not retain an exact denominator such as "66 of 78"; intake changes catalog
size independently of App Store releases and makes that copy stale.

The 1.1.4 release notes should mention:

- Ender-3 S1, FlashForge Adventurer 3 and Anycubic Kobra 2 Neo;
- epoxy-resin build-plate guidance;
- the acceleration safety clamp;
- Elegoo in the primary brand list;
- improved Danish Output/export/error chrome.

Review analytics is operational telemetry, not a user-facing feature, and does
not belong in release notes. App Store Connect remains an owner-controlled
external action; the implementation prepares and verifies copy but does not
submit it. Privacy labels are expected to remain unchanged because the event is
aggregate and common-only, but this must be verified during release rather than
assumed.

## 5. Data and logic change evaluation

| Change | Web impact | iOS impact | UI/UX consequence |
|---|---|---|---|
| Elegoo `primary` flag | Already live and guarded by web contract | Bundled mirror + real-catalog test required | Six primary brands; no new screen or overlay route |
| EN/DA resource seam | None | New localized resources and stable `Strings.Output` API | Top-level Output states become consistent; nested subcomponents remain bounded out |
| Review analytics event | Worker, query and dashboard changes required | Best-effort sender after local state persistence | Owner gains an explicit count; end-user flow and eligibility do not change |
| Metadata copy | No runtime change | No runtime change | Store listing remains accurate as intake grows |

The already-landed `epoxy_resin`, printer and acceleration changes have already
been evaluated across web, intake validation, tests and the iOS mirror. This
release verifies those surfaces; it does not reopen their implementation.

## 6. Failure, privacy and rollback behavior

- Localization lookup failure falls back to English; missing or mismatched keys
  fail tests before release.
- Analytics network or signing failure is silent after local review-request
  state is persisted. It cannot block UI, generate another prompt request or
  collect a richer payload.
- A Worker validation failure remains fail-closed (`400`) and must not write a
  partial event.
- The dashboard must show query failure as unavailable, not as a misleading
  numeric zero. Zero is rendered only from a successful query response.
- The web analytics addition can be reverted independently of the iOS binary;
  an older Worker safely rejects the new event while the app continues normally.
- Elegoo rollback is the same one-field bundled change in a future binary. No
  remote overlay rollback or version-floor change exists in this train.
- Metadata submission remains reversible in App Store Connect until owner
  submission; repository copy is the reviewable source.

## 7. Delivery sequence and release gates

### Sequence

1. Land and production-verify the Worker/query/dashboard analytics contract.
2. Land remaining iOS catalog, localization and analytics work locally under the
   iOS push gate.
3. Prepare durable metadata and release notes.
4. Run all gates against the exact final iOS HEAD.
5. Only when the remaining approved scope is complete and the owner is ready:
   push the next iOS `main` commit(s), dispatch TestFlight, and perform owner
   device acceptance. Earlier 1.1.4 baseline commits and TestFlight builds
   already exist remotely; the gate means **no further iOS pushes from this
   newly approved scope** until the complete train is ready.
6. Owner applies App Store Connect metadata and decides submission.

### Required exact-HEAD evidence

Web:

- complete repository CI/test tiers green;
- analytics Worker validation/index tests green;
- analytics-query and dashboard tests green;
- production smoke confirms the dashboard exposes `Review requests`, including
  a valid explicit-zero state.

iOS:

- complete XCTest suite green;
- all six walkthrough UI scenarios green;
- Release build green;
- XcodeGen regeneration produces no unexplained project drift;
- recursive web/iOS `engine.js` + `data/` parity green;
- exact primary-brand and contiguous-order contract green;
- EN and DA bundle/key/placeholder tests green;
- manual EN/DA Output smoke at supported compact and regular widths;
- unique build number supplied by the established Fastlane timestamp flow.

Owner/TestFlight:

- Elegoo appears in the primary row;
- the three newly bundled printers generate profiles;
- epoxy-resin guidance and persistence work;
- top-level Output/export/error chrome is coherent in English and Danish;
- no claim is made that the StoreKit prompt displayed in TestFlight.

## 8. Explicit non-goals

- No re-entry of Hi [#29](https://github.com/mustiodk/3dprintassistant/issues/29)
  and no printer-intake taxonomy/owner-decision execution.
- No German UI; #37 owns German and the broader future-language architecture.
- No picker personalization or featured-material unification; #32 owns that
  product decision and is deferred beyond 1.1.4.
- No persistent `Rate 3DPA` link before #12 produces evidence.
- No claim that StoreKit displayed or that a user completed a review.
- No review-prompt eligibility, cooldown or TestFlight-suppression changes.
- No `-uitest` state-isolation refactor, My Gear, AI buddy, light mode, account,
  subscription or unrelated roadmap feature.
- No iOS overlay mutation or `min_app_version` raise.
- No CI work for the existing App Store IAP `MISSING_METADATA` warning.
- No whole-app localization promise; this train is bounded to §4.2.

## 9. Issue and completion semantics

- #12 closes only after the production dashboard exposes the request count and
  an explicit successful-query zero.
- #31 closes after the iOS train passes owner acceptance or ships, according to
  the issue's chosen completion rule; web-only delivery is insufficient.
- #35 may close after its already-built cross-surface contract is reverified.
  Closing it does not authorize #29 re-entry.
- The spec becomes `ACCEPTED` only after owner review. An implementation plan is
  written after that approval, not as part of this document.
