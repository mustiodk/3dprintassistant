Must-fix: define bytewise as **UTF-8 bytewise**, not JS `<`, Swift locale sort, or `localeCompare`. The plan already recognizes this for gear ids because JS UTF-16 differs from UTF-8: [plan](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/plans/2026-08-21-train1-web-gear-plan.md:519). Apply the same comparator class to array values.

Must-fix: keep engine order in `gear-validate.js`, not `gear-store.js`. The plan already has the right V7 contract: stored bytewise, resolved in engine order at apply time: [plan](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/plans/2026-08-21-train1-web-gear-plan.md:710).

Should-fix: sync merge should treat string arrays as equal sets as a defensive no-op check, but not as the format answer. It reduces damage if a legacy/buggy client writes unsorted arrays, but it does not solve backups, hand-edited envelopes, iOS Codable round trips, or first-browser-write bytes.

Optional: do not store “user order”. Current web and iOS selection order is click order, not a product semantic: web appends on click at [app.js](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/app.js:1565), iOS appends on tap at [GoalsView.swift](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant-ios/3DPrintAssistant/Views/Configurator/GoalsView.swift:386). Extra user-order storage adds a second ordering surface for no current value.

**Consequences**

Option A’s hidden cost is that the store becomes dependent on versioned engine metadata even if injected rather than imported. That weakens the no-engine-import/golden-proof boundary stated in [gear spec](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/specs/2026-08-20-gear-model-v2-spec.md:235) and [plan](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/plans/2026-08-21-train1-web-gear-plan.md:226). It also makes unknown future ids, old backups, and cardinality changes version-sensitive. If a field later becomes single, the spec says array→single takes the first and degrades: [gear spec](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/specs/2026-08-20-gear-model-v2-spec.md:224). Bytewise gives a stable first; engine-order-at-write gives “whatever engine version last touched it.”

iOS has no GearStore yet, but existing Swift state decoding preserves array order after filtering: [AppStateWebCodec.swift](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant-ios/3DPrintAssistant/Models/AppStateWebCodec.swift:101). Where Swift already needs set semantics, it sorts explicitly: [ProfileKeyHasher.swift](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant-ios/3DPrintAssistant/Models/ProfileKeyHasher.swift:27). So the future Swift gear decoder must implement the same bytewise canonicalizer explicitly.

**Third Option**

No third option beats B. Set-aware sync merge is worth adding later as a guardrail, but it is not a storage format. Storing canonical plus user order is worse: it adds bytes, parallel ordering, label-order hazards, and a future migration surface. If order ever becomes meaningful, that is a structured value and therefore a v2 envelope under the spec’s own migration boundary: [gear spec](/Users/mustafaozturk-macmini/dev/Claude/Projects/3dprintassistant/docs/superpowers/specs/2026-08-20-gear-model-v2-spec.md:113).

Replace the §2.4 Array hygiene sentence with:
